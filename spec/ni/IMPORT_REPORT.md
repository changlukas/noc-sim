## Conflicts

The following inconsistencies exist within the source documents themselves. Please reconcile in the canonical (NI) spec:

### 1. `ERR_STATUS` access mode

- **`06_qos.md §4.1`** declares `ERR_STATUS` access = `RO` (read-only).
- **`06_qos.md §4.4`** says error counters are cleared by writing 1 to `ERR_STATUS[0]`.
- **Action required**: a `RO` register cannot be written. Either change access to `RW1C` (write-1-to-clear), or document a separate `ERR_CLEAR` register, or remove the clear-via-write-1 sentence. The produced `registers.md` flags both interpretations and asks for resolution.

### 2. `URGENCY_STEP` location

- **`06_qos.md §2.4.6`** lists `URGENCY_STEP` (2 bits) as a separate row in the CSR Configuration table for Regulator mode.
- **`06_qos.md §4.1`** Register Summary table does **not** assign an offset to `URGENCY_STEP`.
- **Inferred**: most parsimonious mapping is to consolidate `URGENCY_STEP` into the same word as `BASE_QOS` (offset 0x018). The produced `registers.md` reflects this consolidation but tags it as a `TODO(designer): confirm`.

### 3. NI clock signal

- **`01_overview.md`** describes a single mesh clock and refers to `clk_i` indirectly (e.g., `Throughput = bytes / cycles`).
- **`04_network_interface.md`** never enumerates `ni`'s clocks/resets.
- **Inferred**: single-clock-domain `clk_i`, but this must be confirmed if the AXI side and NoC side might run at different frequencies. The produced `interfaces.md` flags a TODO.

### 4. Compatibility claim

- **`04_network_interface.md §1.3`** says "AMD Versal 風格" (AMD Versal style) for NMU/NSU naming.
- The README must commit to whether `ni` claims compatibility with the AMD Versal NoC NIU register set or only borrows the naming. The produced `README.md` documents the naming claim and flags the remainder as TODO.

## When this spec might **not** be the right starting point

Reviewing the imported content, the noc-sim documentation describes a **C++ behavior model** that mirrors a hardware NoC. If the eventual goal is the C++ model spec (rather than RTL), some sections of this import are over-specified — `theory_of_operation.md`'s reset/CDC discussion and `interfaces.md`'s signal-level decomposition are RTL concerns. Conversely, several behavioral nuances in the C++ model (transaction-level matching tolerance, scoreboard semantics) are under-represented in the imported spec because they live in `08_simulation.md` (not pulled).

Before investing in closing all 36 TODOs, decide: **is this an RTL spec or a behavioral-model spec?** The hw-spec-author plugin is designed for the former. If the latter, several of the `TODO(designer):` markers — especially around clocks, resets, and signal-level interfaces — are not actually relevant and should be marked "out of scope: behavioral model" instead of left as gaps.
